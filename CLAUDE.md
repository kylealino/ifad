# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

This repo is the **IFAD Portal** (Integrated Finance and Administrative Division ERP), a CodeIgniter 4 app for a government office. One sign-in opens a portal of systems, numbered as on the FAD ERP diagram:

1. **FODS** (Financial Obligation and Disbursement System): budget allotment, ORS/BURS obligations, disbursement vouchers, cashier outputs (LDDAP-ADA, ADA, RCI), procurement (PPMP, PR, PO, Abstract), the SAOB report, and maintenance data (payees, projects, UACS, users/roles). Most of this file is about FODS.
2. **SORF** (Document Request System: special order / travel order requests, approval, HR desk, Special Order documents), brought in from the standalone `htdocs/sorf` project. See "IFAD Portal and SORF" below.
3. to 6. Resource & Facilities Management, Quality Management (QMIS), Human Resource Management (IHRMIS, Integrated Human Resource Management Information System), Integration & Management (shown to users as "Admin & Oversight", tab "Admin"): listed as "coming soon".

## Running it

- Runs under **XAMPP** (Apache + MariaDB/MySQL, PHP ≥ 8.1) at `http://localhost/fods-local/public/` (`app/Config/App.php` `baseURL`, `indexPage = ''`).
- DB: MySQLi on localhost (`app/Config/Database.php`): the `default` group is FODS (and the portal accounts), and the `sorf` group is SORF's own database (locally `sorf-staging`). SORF code always connects with `\Config\Database::connect('sorf')`, and never joins across the two databases. `.env` sets `CI_ENVIRONMENT = production` (so errors are not shown in the browser) and the FODS Assistant's `GROQ_API_KEY`, `GROQ_MODEL` and `GROQ_FALLBACK_MODEL`. `.env` is git-ignored: each server keeps its own. The root `.htaccess` blocks web access to everything outside `public/` that must stay private (`.env`, `.git`, `*.sql`, `__db_backup/`, `*.md`, tooling files); deploy it with the code. Check `writable/logs/log-YYYY-MM-DD.log`. The README's `.env` database setup is out of date: the DB settings live in `Database.php`.
- The framework is vendored in `system/`, and there is no `vendor/` directory. Composer/PHPUnit aren't installed, and `tests/` only has the CI4 sample tests. Verify changes by loading the page in the browser, and run `php -l <file>` for syntax.
- There are no CI4 migrations. Schema changes go in hand-written, re-runnable SQL files at the repo root (`migration-<topic>-MMDDYYYY.sql`). `fods-local.sql` is the full current dump, and `__db_backup/` holds older dumps. Take a backup dump before you run a migration. Local is MariaDB but **staging is MySQL 8**, so migrations must run on both: no `ADD COLUMN IF NOT EXISTS` (MariaDB-only); guard each column with an `information_schema` check and `PREPARE`/`EXECUTE`, as `migration-staging-sync-09302026.sql` does.

## Architecture

The app uses one controller, one model, one view folder and one JS file per module. It does **not** use idiomatic CI4: there's no query builder, no resource routes, no entities and no foreign keys.

| Piece | Location |
|---|---|
| Routes | `app/Config/Routes.php`. Each module has a GET and a POST route to `MyX::index` with `['filter' => 'myauthuser']` |
| Sidebar | `app/Config/Navigation.php` (data-driven). Rendered by `app/Views/templates/myheader.php`, which shows only the items the user can access |
| Access codes | `app/Config/AccessCodes.php` constants. Never hardcode the literal codes |
| Access checks | `app/Helpers/access_helper.php` (`fods_has_access`, `fods_has_any_access`, `fods_require_access`, `fods_current_user`), autoloaded through `Config\Autoload::$helpers` |
| Auth filter | `app/Filters/Myauthuser.php` checks the session key `__xsys_myuserzicas_is_logged__` |
| Controllers | `app/Controllers/MyX.php`. `index()` switches on `getPostGet('meaction')` (`MAIN`, `MAIN-SAVE`, `MAIN-LOAD`, `MAIN-DELETE`, `PRINT-*`, …) |
| Models | `app/Models/MyXModel.php`, with raw parameterized `$this->db->query("... ?", [...])` |
| Views | `app/Views/<module>/<module>-main.php`, wrapped in `templates/myheader.php` / `myfooter.php` |
| PDFs | `*-pdf.php` views that `require APPPATH . 'ThirdParty/fpdf/fpdf.php'` and draw with FPDF |
| JS | `public/assets/js/<area>/<module>.js`, each with one global `function __mysys_x_ent(){...}`. Shared helpers are in `public/assets/js/mysysapps.js` |
| CSS / layout | `public/assets/css/fods.css` (layout + UI kit), `public/assets/js/fods-layout.js` (sidebar) |
| Misc helpers | `app/Models/MyLibzSysModel.php` (string sanitizers, date formatting, select/pagination HTML) |

### Request/response conventions
- Constructors repeat the same boilerplate: `$this->request`, `$this->myx = model(...)`, `$this->db`, `$this->session`, and `$this->cuser = session('__xsys_myuserzicas__')` (the username).
- Saves are AJAX POSTs. The model echoes a `<script>` block (toastr + redirect, or an error alert) and then calls `exit;`, and the JS injects that HTML into an output div. Save payloads use a legacy `"a|b"` delimited format. Keep it byte-identical.
- Every insert/update/delete/approve branch in a model starts with `fods_require_access(\Config\AccessCodes::X_ACTION, 'Saving'|'Updating'|'Deleting'|'Approve'|...)`. `MAIN` checks `fods_has_access(X_VIEW)` and otherwise returns `view('errors/html/access-restricted')`.
- **Modernized modules** (User Mgmt, Payee, Supplies/Products, Project, UACS, Budget Allotment/Approval, ORS and BURS Entry/Approval, Disbursement/Disbursement Approval, LDDAP-ADA/ADA and their Approval pages, RCI, SAOB, PPMP, PR and PR Approval, PO and PO Approval) use a list page (page head, stat tiles, filter pills, client-side DataTable from a JSON var). An editor modal loads through `MAIN-LOAD` JSON. Approval pages use a review modal with a two-step certify/disapprove, where remarks are required to disapprove. All of these list pages share one card layout, computed in each module's JS from the list data for the year picked in the page head (default: the current year, remembered per page; "All years" is an option): **Pending** (on approval pages: "Waiting for you", meaning only the steps the user can act on), **Returned** (disapproved), **Approved**, and **Total amount**. Each card also filters the list. Budget drafts are a filter pill, noted under Total. Only Abstract still uses the older single form + table layout.
- **ORS and BURS are twins.** They share the same schema (`tbl_burs_*` mirrors `tbl_ors_*`) and the same code with the names swapped. Keep them in sync. The only BURS differences are: FC 07 projects (`fundcluster_id='2'`), blank default particulars, and the BURS form labels. ORS certification goes Box A → Box B, and both steps use the one `ORSAPPROVAL_APPROVE` (38005) code. A certified ORS is locked, and editing a disapproved one resets it to Box A.
- **Disbursement** follows the same pattern. A DV is prepared from an ORS or BURS: `OBLIGATION-LOAD` copies the header and deductions, and sums the lines per responsibility code. Saving writes the DV no. back to that ORS/BURS by `serialno`. Approval is three steps in order: Box A (supervisor) → Box C (accounting) → Box D (approved for payment), stored in the `certa`, `certc` and `certd` columns (statuses `pending_a`, `pending_c`, `pending_d`, `approved`, `disapproved`). All three use the one `DISBURSEMENTAPPROVAL_APPROVE` (40005) code, but a step can only be decided by the signatory named on that box, matched on `myua_user.full_name` (`certified_a`, `certified_c`; Box D is not stored and follows the net amount through `MyDisbursementModel::box_d`, which the PDF also uses). The Administrator role (`fods_is_admin()`) can decide any step. The rule lives in `MyDisbursementModel::can_decide`. A DV is locked once Box A approves it, and editing a disapproved one sends it back to Box A. Every change is logged to `tbl_disbursement_history`, which the editor and the review modal show as a timeline. DV tax rules round each amount to 2 decimals before totaling, which is different from ORS. A DV can have several **other deductions** under any category (Goods, Services, Manual, Payroll, Income Tax; added on top of that category's own deductions) (type + amount each, e.g. a delay penalty per sales invoice) in `tbl_disbursement_deduction` (keyed by `disbursement_id`); the header keeps `other_deductions` as their sum and `deduction_name` as their types joined with "; ", so totals, net, approvals, LDDAP-ADA/RCI and reports read the same fields as before. The save payload adds `dvdeductions_posted=1` plus one `type x|x amount` row each in `dvdeductiondata[]`; a DV saved before this (or copied from an ORS/BURS, which has one) shows its header deduction as one row (`MyDisbursementModel::deduction_rows`). The printout puts each on its own line between NET and Amount Due.
- **LDDAP-ADA and ADA** each have a single approval step (`LDDAPADAAPPROVAL_APPROVE` 41005, `ADAAPPROVAL_APPROVE` 42005). The approval columns are `is_pending`, `is_approved`, `is_disapproved`, `approver` and `remarks` on `tbl_lddapada_hd` and `tbl_ada`. An approved record is locked, and editing a disapproved one sends it back to pending. An LDDAP-ADA line's allotment class is the largest-amount UACS on that DV's own ORS/BURS (`MyLDDAPADAModel::dv_lines`). A line's **withholding tax** is the DV's taxes only (VAT/EWT/PT, WTAX, income tax): its total deductions less its other deductions and its non-tax payroll deductions (SSS, HDMF, Pag-IBIG MP2/loan, HMO), `MyLDDAPADAModel::WITHHOLDING_SQL`; the net stays the DV's net, so gross − withholding need not equal net. The printout applies the same rule to lines saved before this (those still holding the DV's full total deductions); any other stored amount prints as saved. ADA prints by `recid` (`dvno` still works for old links). The LDDAP-ADA printout's four signatures (Certified Correct, Approved, Agency Authorized Signatory 1 and 2) are picked on the entry from the fixed list `MyLDDAPADAModel::SIGNATORIES` (name => position; picking a name fills in its position, which stays editable). They are stored in `certified_by/_position`, `approved_by/_position`, `ada_approver` (signatory 1, the ADA approver shown on LDDAP-ADA Approval, default JOVY S. MEDINA) `/ada_approver_position` and `ada_approver2/_position`. `signatures_for` gives older LDDAP-ADAs (blank columns) the previous fixed names. These are for printing only; who can approve is still the 41005 access right.
- **RCI** has no approval step. Its cards are Reports, LDDAP-ADAs covered, DVs paid and Total amount, and its year is the encoded date (`created_at`/`created_by`, not `added_*`). Picking an LDDAP-ADA adds one line per DV (`MyRCIModel::lddapada_lines`, which takes the responsibility code from the DV's ORS/BURS). The save payload is 12 `x|x` fields per line.
- **SAOB** (`mysaobrpt`) has no approval step either. The page has two tabs: **Allotments** (cards: Allotments, No revisions yet, With revisions, Approved budget; year = `current_year`) and **Reports** (SAOB PDF/CSV, ORS extraction CSV, monthly report CSV and status PDF, all on their old endpoints). An allotment is one program/project for a year with PS, MOOE and CO lines (`tbl_saob_{ps,mooe,co}_dt`), each carrying 12 `<month>_revision` columns. Revision months (`is_jan` … `is_dec` on `tbl_saob_hd`) are switched on in order; the revision month is the last of an unbroken Jan..N run (`MySaobReportModel::revision_month`, mirrored in JS). A line's proposed realignment is written to that month's column only when the month is switched on by that save; saving again keeps what is recorded. January on locks the approved budget, and the total revised allotment must equal the total approved budget. The save payload is 19 `x|x` fields per line (object code, particulars, UACS, approved, to-date, proposed, revised, then the 12 monthly revisions). The header and its lines are saved in one transaction. "Copy" starts a new allotment from an old one's codes (`?reuse_recid=` still works).
- **PPMP** (`myppmp`, save action `PPMP-SAVE`) has no approval step. Its status comes from two switches on `tbl_ppmp_hd`: `final` (wins when both are on), `indicative`, or `unmarked`. Cards are PPMPs, Indicative, Final and Estimated budget; the year is `fiscal_year`. Items are in `tbl_ppmp_dt` (keyed by `ppmp_id`, and carrying `ppmpno`). The save payload is 15 `x|x` fields per item. Quantity × unit cost fills the estimated budget only until someone types a budget.
- **PR** (`mypr`, main action `PR-MAIN`, save `PR-SAVE`) has two statuses. Its procurement status (`MyPR::statusOf`) is `unnumbered` (no PR no.), `numbered`, or `rfq` (at least one RFQ). Its approval (`MyPR::approvalOf`) works like ORS/PO: Box A (requesting office, `requested_by`, picked on the Certification tab from active `cert_tag = 1` users and PPMP signatories; position taken from that user record) → Box B (`approved_by`, not picked: set on save from the estimated cost by `MyPRModel::approver_for` with the PO's `APPROVAL_LIMIT` — below 5M ALEXIS M. ORTIZ / Chief Administrative Officer, FAD; 5M and above ATTY. LUCIEDEN G. RAZ / Director III). The saved `estimated_cost` is the server-side sum of the lines (quantity × unit cost rounded per line), so it always matches Box B. Decisions happen on **PR Approval** (`myprapproval`, family 45: `PRAPPROVAL_VIEW` 45001, `PRAPPROVAL_APPROVE` 45005), each box only by the signatory named on it or an Administrator (`MyPRModel::can_decide`). A PR is locked once Box A approves it (`MyPRModel::is_locked`) except for its PR no., which can still be set ("Save PR no."); editing a disapproved PR sends it back to Box A. The PR printout uses the saved signatories (PRs saved before PR approval print the old fixed names). PR approval does not gate the PR no., RFQs or the PO. Anyone who can save PRs (`PR_ADD` for a new PR, `PR_UPDATE` for a saved one) sets the PR no.; there is no procurement-only rule any more. RFQs are open to everyone: `PR_VIEW` to see and print them, `PR_UPDATE` to add one, and the PR must already have a PR no. A PR takes its items from the PPMPs picked (`tbl_pr_ppmp`): `LOAD-PPMP` returns their items summed per description and unit. Adding or removing a PPMP replaces the items; opening a saved PR shows its saved `tbl_pr_dt` lines, with "Reload from PPMP" to refresh them. RFQs (`tbl_pr_rfq`) are filed under the PR no. string, not the PR's `recid`. The save payload is 5 `x|x` fields per item.
- **PO** (`mypo`, Purchase Order, family 43, tables `tbl_po_hd` / `tbl_po_dt`) is prepared from a numbered PR: `PR-LOAD` copies its PR no., date, charge-to, end-user, fund cluster and items (blank lines skipped) and returns its RFQs, one of which fills the supplier and the delivery / payment terms. The PO keeps `pr_id` only when the PR was picked from the list. PO nos. must be unique. The server computes each line's amount (quantity × unit cost rounded to 2 decimals) and the PO total; the save payload is 5 `x|x` fields per item (stock no., unit, description, quantity, unit cost). **Approval works like ORS**: Box A (accounting, `accountant` picked from active `cert_tag = 3` users, default Bonjobie; position taken from that user record) → Box B (approval, `approved_by`, not picked: set on save from the total by `MyPOModel::approver_for` — below `APPROVAL_LIMIT` 5,000,000 ALEXIS M. ORTIZ / Chief AO, FAD; 5,000,000 and above ATTY. LUCIEDEN G. RAZ / Director III; the JS mirrors it live). Columns `is_pending`, `is_approved_cert{a,b}`, `is_disapproved_cert{a,b}`, `cert{a,b}_remarks`, `cert{a,b}_approver`; statuses `pending_a`, `pending_b`, `approved`, `disapproved`. Decisions happen on **PO Approval** (`mypoapproval`, family 44: `POAPPROVAL_VIEW` 44001, `POAPPROVAL_APPROVE` 44005), and each box can only be decided by the signatory named on it (matched on `myua_user.full_name`) or an Administrator (`MyPOModel::can_decide`, same rule as the DV). A PO is locked once Box A approves it; editing a disapproved one sends it back to Box A (and recomputes Box B). The printout (`PRINT-PO` on both pages, `procurement/po/po-pdf.php`) is Appendix 61 / FAD-PS-006 on legal paper with the `fnri-header.png` letterhead. The older blank PO template under Abstract (`PO-PRINT`) is unrelated.
- **FODS Assistant** (no access code: everyone signed in has it; no page or sidebar entry) is a floating chat button + panel in the lower right of every page, rendered by `templates/myfooter.php` and driven by `assistant/fods-assistant-panel.js`; the chat UI is the component `assistant/fods-assistant.js` (`FodsAssistant.mount`) + `css/fods-assistant.css`. Questions go to `myassistant?meaction=ASK` (controller `MyAssistant`, model `MyAssistantModel`); opening `myassistant` otherwise redirects to the dashboard. It is an AI chat over FODS data through Groq's OpenAI-compatible API (key and models in `.env`). The AI never writes SQL: it can only call six read-only "tools" in the model (`get_overview` = the Dashboard's `MyDashboardModel::summary`, `search_obligations`, `search_disbursements`, `my_pending_approvals` (reuses each module's `statusOf` / `can_decide`), `search_payees` (never account numbers or TINs), `search_procurement`), each with fixed parameterized queries that first check the asking user's own module access, so it sees only what that person can open. Answers are capped (rows, result size), use `reasoning_effort: low` on gpt-oss, and switch to `GROQ_FALLBACK_MODEL` when the main model hits its per-minute token limit (429). Per-user limit `RATE_PER_MINUTE` (12). Every question is logged to `tbl_assistant_log` (question, lookups used, status, model; not the answer). The conversation lives in the browser tab (sessionStorage); the last 12 turns go with each question. Answer formatting escapes all HTML before applying a small markdown subset. **Links:** each tool result carries a `link` per record (its editor, e.g. `mydisbursement?meaction=MAIN&recid=`) and, for ORS/BURS, DVs, PRs and POs, an `approval_link` (`<approval page>?recid=`, which opens its review modal; `null` unless the user can open that page); the system prompt lists the pages from `fods_nav()`. The JS turns a markdown link into an anchor only when its target is a relative FODS route (`SAFE_LINK` in `fods-assistant.js`); anything else stays plain text. When the assistant panel is open, the body has the class `fods-ai-open`. Free Groq keys allow about 8,000 tokens/min per model (roughly 1-2 answers a minute each), shared by everyone.
- **Dashboard "Find a record"** (top of `mydashboard`, `meaction=SEARCH&q=&type=all|ors|burs|dv|lddapada|rci`, `MyDashboardModel::search`) searches ORS, BURS, DV, LDDAP-ADA and RCI as you type, only in the modules the user can view (`MyDashboardModel::SEARCH_TYPES`). It matches numbers, payee, particulars, and for LDDAP-ADA / RCI their lines' DV no., ORS no. or payee. It shows 5 per type under All (25 for one type); a group with an exact number match comes first and Enter opens its first result. Each result opens the record through its page's `?recid=` deep link.
- **Editor modals are reused across records**, so lock code must set `disabled` both ways (see `applyLocks` in the SAOB, PPMP and PR scripts), not only disable.
- **Messages** (`mymessages`, the speech-bubble icon in the topbar, not in the sidebar) is chats only. Everyone can chat (direct or group, `tbl_conversation_hd/_member/_msg`, unread = messages after the member's `last_read_id`; `is_archived` on the member row hides a chat for that person only, and any new message unarchives it for everyone; the person who created a group chat (`tbl_conversation_hd.added_by`) can remove members through `CONV-REMOVE`, which logs an `is_system` note in the chat; images and files go in `tbl_conversation_attachment` under `writable/uploads/chats/<year>/`, served by `meaction=CHAT-FILE` to members only). **Seen and typing:** `tbl_conversation_member.last_read_at` is stamped whenever `last_read_id` moves forward (opening/polling the chat, or replying), so your latest message shows "Sent" / "Seen 2:31 PM" (direct) or "Seen by N of M" plus each reader's initials under the last message they read (group). `typing_at` is set by `CONV-TYPING` (the page pings at most every 3 s while the box has text, and clears it when emptied, sent, or you leave); a member counts as typing for `MyMessagesModel::TYPING_SECONDS` (6) after the last ping. The open chat polls `CONV-LOAD` every 2.5 s while the tab is visible (hidden tabs don't poll, so they don't mark messages read). **Chat heads** (Messenger-style, every page, 768 px and wider; `messages/fods-chatheads.js` + `css/fods-chatheads.css`, container `#fodsChatHeads` in `templates/myfooter.php`) use the same `mymessages` actions, so there are no tables of their own. Clicking a chat in the topbar dropdown opens it in a window docked at the bottom right (up to 1-3 by screen width; more minimize to round heads with unread badges, at most 6). Each window polls `CONV-LOAD` with `after_id` every 3 s, sends, attaches/pastes files, and shows typing and seen. `fods-inbox.js` checks chats every 20 s and fires the `fods:convs` event, which pops a head for any chat with a new unread message. Open and minimized chats are kept in sessionStorage (`fods.chatheads.<user>`), so they come back on the next page. On the Messages page they show only chats popped out with the chat's **Open as chat head** button (`#msgPopout`, which carries any unsent text over); new-message heads don't pop there, the topbar dropdown opens chats in the page, and opening a chat in the page closes its head. **Pasting files:** Messages, chat heads and Helpdesk attach clipboard files and screenshots (Snipping Tool, Win+Shift+S; read from `clipboardData.files`, or `items` when that is empty) pasted anywhere in the open chat, ticket or form, not only in the text box (`pasteFiles(scope, picker, when)` / `clipboardFiles` in each script). Nameless or `image.png` shots are renamed `screenshot-YYYYMMDD-HHMMSS.png`.
- **Notifications** (the bell in the topbar, before Messages; everyone signed in; no page: `mynotifications` (GET, controller `MyNotifications`) answers only `meaction=INBOX`, anything else goes to the portal). `MyNotificationsModel::inbox()` lists what is waiting for the user to act on, one group per module with a count, a link to its approval page and its oldest record: FODS approval steps they can decide (`MyAssistantModel::pending_approvals()`, the assistant's `my_pending_approvals`, so the same `statusOf` / `can_decide` rules) and SORF requests waiting for their "Noted by" (`drf_approval_count()`). Nothing is stored; the result is cached in the session for `CACHE_SECONDS` (45), and `&fresh=1` (sent when the dropdown opens) skips the cache. The badge is not rendered with the page: `fods-inbox.js` loads it after the page, then polls every minute. `mynotifications` is in `Config\Systems::$shared`, so polling it doesn't change the remembered system.
- **Helpdesk** (`myhelpdesk`, controller `MyHelpdesk`, model `MyHelpdeskModel`, view `helpdesk/helpdesk-main.php`, script `helpdesk/myhelpdesk.js`; the lifebuoy icon beside Messages in the topbar) holds support tickets (`tbl_ticket_hd`, thread in `tbl_ticket_dt` whose first row is the description and `is_system` rows are status notes, plus `tbl_ticket_attachment` and `tbl_ticket_seen`). Everyone can file tickets and follow their own under **My tickets**, where each ticket is a chat-style conversation with support. `TICKET_VIEW` 37001 opens the **Support desk** tab: cards (Open, Waiting for a reply, In progress, Resolved/closed), breakdowns by type, priority and module, and every ticket in a table that opens in a review modal. `TICKET_UPDATE` 37003 adds replying as support and changing status. The requester can only close or reopen. A row's `needs_reply` means the requester spoke last on an open ticket. Saving a ticket closes the form and reloads the list. Images only (JPG/PNG/GIF/WEBP, 5 x 5 MB), stored under `writable/uploads/tickets/<year>/` and served only through `meaction=ATTACHMENT` after a ticket access check. Old ticket links to `mymessages` (`tab=tickets|desk`, `ticket=`, `meaction=ATTACHMENT`) redirect to `myhelpdesk`; a bare `new=1` stays on Messages (New message). **Shared pieces:** file-upload validation and storage for both live in `MyUploadsModel` (allowed types checked against the file's real content); the chat-style styles in `public/assets/css/fods-chat.css`. `templates/myheader.php` renders both topbar badges (unread chats; tickets with news) and `public/assets/js/fods-inbox.js` polls both. The old `Support` controller (`tbl_support_*`) is superseded and no longer linked.

## IFAD Portal and SORF

- **Portal:** `portal` (`Portal` controller, `portal/portal-main.php`) has **no sidebar** (the brand sits in the topbar; only FODS and SORF pages have one). It is the system picker plus a short guide, sized to fit the window with no scrolling (keep it that way: the view passes `bodyClass` `ifad-fit`, and fods.css then makes `.fods-page` exactly 100vh with the tile grid taking the rest in equal rows; tablet width and 560px height and up): a navy greeting band (greeting, one-line purpose, date) with **Ifa**, an inline-SVG guide character whose speech bubble cycles tips (built in the view; click it or "Next tip"; auto-advances every 9 s, not with reduced motion; the tips carry the "how to get around" info; Ifa stays put and each tip names a CSS selector whose element gets a 4 s amber ring, `.ifad-spot`), then a tile per system in diagram order (all six the same size, three across in two rows that stretch to the screen height, each listing its `steps` from `Config\Systems`; every enabled tile shows its number key), then one strip with the request flow and the four values. No Messages / Helpdesk / My Account links (they are in the topbar). Tiles the user can open link to their start page and also open with the system's number key (1, 2, ...); coming-soon systems are enabled too (white `.is-open.is-dev` tiles, stage badge from `ifad_stage()`: "In development" (amber) or, for a system with `stage` `integration` such as IHRMIS (an existing system reached through its API), "Integration in progress" (blue; its preview page says "is being connected" / "What it covers"), "Preview <name>" + number key 3-6, opening their `portal/<key>` page); only live systems the user can't open are greyed out with "No access". Motion is CSS only (a 250 ms fade-up, transform/opacity hovers) and never delays opening a system. Systems come from `Config\Systems` (number, area, name, short name, icon, tone, `live`/`soon`, the diagram's steps, and `tip`: what Ifa says about it; Ifa's tips are hello, one per system, then getting around). Step chips that don't fit a tile are hidden whole behind a "+N more" chip (`fitSteps` in the view), never cut mid-line. Sign-in lands on this page; right after login (`ifad_after_login` flash) someone who can open only one system goes straight into it. `/` sends a signed-in user to the portal. Login page and page titles say "IFAD Portal". The sign-in page (`MyLogin.php`, standalone, its own inline CSS) mirrors the portal: the same system names (`short`), stage labels from `ifad_stage()` (Live; In development, amber; Integration in progress, blue), the portal's tagline and four values, and Ifa standing beside the system list (feet level with its last row) with sign-in tips (1440px and wider). Ifa's drawing is one shared partial, `portal/ifa-mascot.php`, used by both pages (each animates its `m-*` parts in its own CSS).
- **Who opens what** (`app/Helpers/ifad_helper.php`, autoloaded): `ifad_can_open('fods')` = any FODS access code; `ifad_can_open('sorf')` = an active SORF member row with a role that opens at least one SORF page. `ifad_home()` is each system's start page, `ifad_current_system()` the system of the current page (`sorf/...` = sorf, `portal`, the shared pages Messages / Helpdesk / My Account keep the last system in session `ifad_system`, everything else = fods). The FODS dashboard and the AI Assistant are only for people who can open FODS.
- **Header** (`templates/myheader.php`): brand "IFAD Portal" with the current system's short name, and the **system tabs** at the left of the topbar (`.ifad-tabs`): one tab per system the user can open (current one highlighted), so switching is one click, then a tab per coming-soon system (`.ifad-tab.is-soon`: muted, amber dot, after a divider; icon only below 1400px unless current; labels use the system's optional `tab` key, e.g. "Facilities", "Admin", else `short`), plus a grid button back to the portal page. Live systems they can't open appear only on the portal page. **Coming-soon pages:** `portal/<key>` (`Portal::soon`, view `portal/portal-soon.php`, route `portal/(:segment)`) is a system's "under development" page: what it is (its `tip`), an indeterminate "building" bar (no progress figure: there is none to show), what it will cover (`steps`), no action buttons (only the "All systems" link at the top; the topbar tabs do the rest), and an animated SVG scene (Ifa in a hard hat tapping with a wrench, gears, blocks stacking; CSS only, off for reduced motion). It fits the window like the portal (`ifad-fit`) and has no sidebar (`myheader.php` gives none to coming-soon systems). The coming-soon tabs and the portal's coming-soon tiles link to it; a live or unknown key redirects. On phones the tabs show icons only. The sidebar is `ifad_nav($system)`: FODS = `Config\Navigation::$groups` (as before), SORF = `Config\Navigation::$sorf` (items by SORF permission, `count` = approvals badge), the portal = no sidebar. Pages can pass `ifadSystem`, `pageTitle`, `sorfNav`, `headExtra` to the header and `footHtml`, `footScripts` to the footer.
- **Accounts:** one sign-in for everything, in FODS `myua_user` (no self-registration). The login stores the username exactly as saved, regenerates the session id, and accepts bcrypt hashes (`$2y$`, SORF accounts brought over) as well as SHA-512. A person's SORF access is their **member row** in the SORF database (`sorf.myua_user`, same username): `role_id` (SORF role), `is_active` (SORF on/off), SORF division/section (remembered from their last request); its `full_name`/`position` are a copy of the portal account, refreshed by `drf_current_user()`; its password column is unused. The SORF role is set in FODS **User Management** (a "Document Request System (SORF) role" select; `MyUserManagementModel::syncSorf` -> `App\Models\Sorf\SorfMemberModel::set_role`); renaming a username there renames it everywhere in the SORF database (`SorfMemberModel::rename`). What each SORF role may do is edited in SORF's own Roles & Permissions page (`sorf/myroles`, permission `admin.roles`); SORF's "Manage users" permission and its Users / My Account / login / register pages are gone.
- **SORF code** lives in its own folders: `app/Controllers/Sorf` (namespace `App\Controllers\Sorf`, base `SorfBaseController`), `app/Models/Sorf`, `app/Libraries/Sorf` (DocHtml, DocWord, RequestPdf, SignatureStore), `app/Config/Sorf` (`Config\Sorf\Permissions`, `RequestForms`, `DocumentTemplates`), `app/Helpers/drf_helper.php` (autoloaded: `drf_current_user`, `drf_can`, `drf_home_path`, `sorf_url()`), `app/Views/sorf`, `public/assets/sorf` (drf.css, drf-doc.css, drf-app.js, page scripts, letterhead images), `public/assets/libs/pdfjs`. Uploads go to `writable/uploads/sorf/{signatures,requests}/<year>/`.
- **SORF routes:** the `sorf` group (`Routes.php`), filters `myauthuser` + `sorfaccess` (`App\Filters\SorfAccess`: no SORF access = back to the portal with a notice). Pages keep their SORF names under the prefix: `sorf/myrequest`, `sorf/myapproval`, `sorf/myhrrequest`, `sorf/myhrdoc`, `sorf/myroles`; `sorf/` goes to the user's first SORF page. PHP links use `sorf_url('myrequest?...')`; SORF scripts build URLs with `__mysys_drf.url(path)` from the `drf-siteurl` meta, which `sorf/templates/sorf-header.php` sets to `.../sorf/`.
- **SORF pages** render inside the portal layout: `sorf/templates/sorf-header.php` calls `templates/myheader.php` (SORF sidebar, `drf-siteurl` and `drf-csrf` metas, drf.css recoloured to the portal palette by mapping `--drf-navy*` to `--fods-teal*`) and wraps the page in `.drf-body.drf-content.ifad-sorf`; `sorf-footer.php` adds SORF's confirm and print modals and loads drf-app.js and the page's `scripts` after Bootstrap.
- **CSRF:** on for `sorf` and `sorf/*` only (`Config\Filters::$filters`), session-based and not regenerated per request (`Config\Security`), because SORF's scripts read the token once per page (`X-CSRF-TOKEN`). FODS pages are not covered yet.
- **Migrations:** `migration-ifad-portal-sorf-10282026.sql` (SORF database: renames the SORF accounts of people who have a FODS account to their FODS username, everywhere; check its pairs per server) then `migration-ifad-portal-fods-10282026.sql` (FODS database: a portal account, with no FODS role, for every SORF member without one, keeping their bcrypt password; set `@sorf_db`). Adding a system 3-6: its entry in `Config\Systems` (`status` `live`), its access rule in `ifad_can_open()` and start page in `ifad_home()`, a menu for `ifad_nav()`, its own namespace/folders/database group like SORF.

## Access control (RBAC)

- Code format: `<2-digit family><3-digit action>`. Actions are 001 View, 002 Add, 003 Update, 004 Delete, 005 Approve. Families run from 20 Payee through 35 RCI, plus 36 Budget Approval, 37 Support Tickets, 38 ORS Approval, 39 BURS Approval, 40 Disbursement Approval, 41 LDDAP-ADA Approval, 42 ADA Approval, 43 Purchase Order, 44 PO Approval and 45 PR Approval. **Every approval page is its own module with only View (which opens the page) and Approve**. Entry modules never carry approve codes. On the approval pages, view-only users see a read-only review. **A new module takes the next family number (46)**, gets constants in `AccessCodes.php`, and gets rows in `tbl_access_modules` named `"<Module> - <Action>"` (the permissions modal splits on `" - "`).
- `tbl_roles` + `tbl_role_access` define roles, and `myua_user.role_id` assigns them. `tbl_user_access` is a per-user **cache** that `MyUserManagementModel::syncUserAccess` regenerates, and the helper reads from it.
- Signatory flags on `myua_user` (`ada_tag`, `cert_tag`, `is_ppmp_signatory`) are separate from module access. None of them is **on the user form**: a new user gets 0 for all three, saving a user never changes them, and they are set directly in the database. Passwords are SHA-512 in `hash_password`, and `is_active` is enforced at login.

## Database conventions

- `tbl_<module>_hd` (header) / `tbl_<module>_dt` (lines). Budget splits use `_direct_{ps,mooe,co}_dt` / `_indirect_{ps,mooe,co}_dt`.
- Every table has `recid` int PK, `added_by`, and `added_at`/`added_on` datetime. Money is `decimal(25,2)`. Flags are `int(11)` 0/1.
- There are no foreign keys. Tables are joined on matching string values (`dvno`, `payee_name`, …).
- Approval columns repeat in each module: `is_pending`, `is_approved_cert{a,b}`, `is_disapproved_cert{a,b}`, `cert{a,b}_remarks`, `cert{a,b}_approver`.

## Adding a module (checklist)

1. Add GET + POST routes with the `myauthuser` filter.
2. Add an entry to `Config/Navigation.php` with its access code(s). Don't hand-edit the sidebar markup.
3. Add the next access-code family in `AccessCodes.php`, plus a migration SQL that inserts the `tbl_access_modules` rows.
4. Write the controller, model, view and JS using an existing modernized module (e.g. `MyPayee`) as the template.
5. Add a migration SQL for the `_hd`/`_dt` tables.

## Gotchas

- The repo has many stale copies (`*_06102025.php`, `* copy.php`, `*.php-backup09292026`, `report-backup/`). Only the unsuffixed file is live. Don't edit the copies.
- Some routes have no auth filter (`dashboard/saob-session-data`, the CSV exports under `MySaobReport`, `mylogin-auth`). `GET myaccount` is registered twice. CI4 keeps the first route, so GET goes to `MyAccount` and only POST reaches `MyUserAccount`.
- `ExternalApi` and `UacsApi` are small standalone endpoints outside the module pattern.
- An ORS / BURS amount is the sum of its six detail tables (`MyDashboardModel::obligationAmounts`, joined as `LEFT JOIN … a ON a.project_id = h.recid`). The header's `gross_amount` is empty on most older obligations, so don't read it. The detail tables have no index on `project_id`: join the aggregate once rather than using a subquery per row.
