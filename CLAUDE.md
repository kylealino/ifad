# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

FODS (Financial Obligation and Disbursement System) is a CodeIgniter 4 app for a government office. It covers budget allotment, ORS/BURS obligations, disbursement vouchers, cashier outputs (LDDAP-ADA, ADA, RCI), procurement (PPMP, PR, PO, Abstract), the SAOB report, and maintenance data (payees, projects, UACS, users/roles).

## Running it

- Runs under **XAMPP** (Apache + MariaDB/MySQL, PHP ≥ 8.1) at `http://localhost/fods-local/public/` (`app/Config/App.php` `baseURL`, `indexPage = ''`).
- DB: MySQLi, database `fods-local` on localhost (`app/Config/Database.php`). `.env` sets `CI_ENVIRONMENT = production` (so errors are not shown in the browser) and the FODS Assistant's `GROQ_API_KEY`, `GROQ_MODEL` and `GROQ_FALLBACK_MODEL`. `.env` is git-ignored: each server keeps its own. The root `.htaccess` blocks web access to everything outside `public/` that must stay private (`.env`, `.git`, `*.sql`, `__db_backup/`, `*.md`, tooling files); deploy it with the code. Check `writable/logs/log-YYYY-MM-DD.log`. The README's `.env` database setup is out of date: the DB settings live in `Database.php`.
- The framework is vendored in `system/`, and there is no `vendor/` directory. Composer/PHPUnit aren't installed, and `tests/` only has the CI4 sample tests. Verify changes by loading the page in the browser, and run `php -l <file>` for syntax.
- There are no CI4 migrations. Schema changes go in hand-written, re-runnable SQL files at the repo root (`migration-<topic>-MMDDYYYY.sql`). `fods-local.sql` is the full current dump, and `__db_backup/` holds older dumps. Take a backup dump before you run a migration. Local is MariaDB but **staging is MySQL 8**, so migrations must run on both: no `ADD COLUMN IF NOT EXISTS` (MariaDB-only); guard each column with an `information_schema` check and `PREPARE`/`EXECUTE`, as `migration-staging-sync-09302026.sql` does.

## Architecture

The app uses one controller, one model, one view folder and one JS file per module. It does **not** use idiomatic CI4: there's no query builder, no resource routes, no entities and no foreign keys.

| Piece | Location |
|---|---|
| Routes | `app/Config/Routes.php`. Each module has a GET and a POST route to `MyX::index` with `['filter' => 'myauthuser']` |
| Sidebar | `app/Config/Navigation.php` (data-driven). Rendered by `app/Views/templates/myheader.php`, which shows only the items the user can access |
| Access codes | `app/Config/AccessCodes.php` constants. Never hardcode the literal codes |
| Access checks | `app/Helpers/access_helper.php` (`fods_has_access`, `fods_has_any_access`, `fods_require_access`, `fods_current_user`), autoloaded through `Config\Autoload::$helpers` |
| Auth filter | `app/Filters/Myauthuser.php` checks the session key `__xsys_myuserzicas_is_logged__` |
| Controllers | `app/Controllers/MyX.php`. `index()` switches on `getPostGet('meaction')` (`MAIN`, `MAIN-SAVE`, `MAIN-LOAD`, `MAIN-DELETE`, `PRINT-*`, …) |
| Models | `app/Models/MyXModel.php`, with raw parameterized `$this->db->query("... ?", [...])` |
| Views | `app/Views/<module>/<module>-main.php`, wrapped in `templates/myheader.php` / `myfooter.php` |
| PDFs | `*-pdf.php` views that `require APPPATH . 'ThirdParty/fpdf/fpdf.php'` and draw with FPDF |
| JS | `public/assets/js/<area>/<module>.js`, each with one global `function __mysys_x_ent(){...}`. Shared helpers are in `public/assets/js/mysysapps.js` |
| CSS / layout | `public/assets/css/fods.css` (layout + UI kit), `public/assets/js/fods-layout.js` (sidebar) |
| Misc helpers | `app/Models/MyLibzSysModel.php` (string sanitizers, date formatting, select/pagination HTML) |

### Request/response conventions
- Constructors repeat the same boilerplate: `$this->request`, `$this->myx = model(...)`, `$this->db`, `$this->session`, and `$this->cuser = session('__xsys_myuserzicas__')` (the username).
- Saves are AJAX POSTs. The model echoes a `<script>` block (toastr + redirect, or an error alert) and then calls `exit;`, and the JS injects that HTML into an output div. The redirect runs after **1 s** (`setTimeout(..., 1000)`) while the toast keeps `timeOut:2000` (error toasts that stay on the page keep 2500): `public/assets/js/fods-flash.js` (loaded in `myfooter.php`) stores any success / info / warning toast still showing when the page unloads (sessionStorage `fods.flash`) and shows it again on the next page for the time it had left. Save payloads use a legacy `"a|b"` delimited format. Keep it byte-identical.
- Every insert/update/delete/approve branch in a model starts with `fods_require_access(\Config\AccessCodes::X_ACTION, 'Saving'|'Updating'|'Deleting'|'Approve'|...)`. `MAIN` checks `fods_has_access(X_VIEW)` and otherwise returns `view('errors/html/access-restricted')`.
- **Modernized modules** (User Mgmt, Payee, Supplies/Products, Project, UACS, Budget Allotment/Approval, ORS and BURS Entry/Approval, Disbursement/Disbursement Approval, LDDAP-ADA/ADA and their Approval pages, RCI, SAOB, PPMP, PR and PR Approval, PO and PO Approval) use a list page (page head, stat tiles, filter pills, client-side DataTable from a JSON var). An editor modal loads through `MAIN-LOAD` JSON. **Approving happens inside each entry module** (Budget Allotment, ORS, BURS, Disbursement, LDDAP-ADA, ADA, PR, PO): the editor's header shows Approve (ORS/BURS: "Certify Box A/B") and Disapprove for whoever may decide the step it is at, and they open the shared confirmation `public/assets/js/fods-decision.js` (`FodsDecision.open({host, mode, verb, title, subtitle, facts, submit})`, loaded in `myfooter.php`; it sits inside the record window and dims it, shows the record, its amount, the step and the one after it, takes remarks (optional to approve, required to disapprove as "Reason for returning"), Ctrl+Enter confirms, Esc closes only it). Each module's `__x_decision` builds the facts and posts `recid`, `remarks` and the `meaction` the module's decide method takes. Who may decide: the module's approval Approve code while pending (ORS, BURS, Budget, LDDAP-ADA, ADA), or the record's `can_decide` from `MAIN-LOAD` (DV, PR, PO: the signatory named on the box, or an Administrator). ORS, BURS, DV and Budget post to their entry route (which has the `MAIN-APPROVE*` / `MAIN-DISAPPROVE*` actions); LDDAP-ADA, ADA, PR and PO post to their `my*approval` route. The decide methods redirect back to the entry page. The old approval pages (`my*approval`) are not in the sidebar any more: opening one redirects to its entry page (`?recid=` kept, so old links and the Assistant's `approval_link` still open the record); their routes stay for the decide/print actions. An entry page (and its `MAIN-LOAD` / prints) opens with the entry View **or** the approval View code, so approvers without entry rights see it read-only. All of these list pages share one card layout, computed in each module's JS from the list data for the year picked in the page head (default: the current year, remembered per page; "All years" is an option): **For approval**, **Returned** (disapproved), **Approved**, and **Total amount**; the pills start with **All records**. Keep UI wording formal: no "Waiting for you", "Pending" as a label, or similar. Each card also filters the list. Budget drafts are a filter pill, noted under Total. A Budget allotment is decided only while it waits for approval (tagging `For Approval`, pending, not yet decided; `MyBudgetAllotmentModel::budget_decide`, which also requires remarks to disapprove), and saving a returned one sends it back for approval (`RESUBMITTED`). A payee name belongs to one payee only (case and outer spaces ignored), checked when a payee is added or renamed (older duplicates can still be edited). The same rule (set or changed only) keeps these unique: DV no., LDDAP-ADA no., ADA no., RCI report no., PO no., usernames, role names, and the ORS / BURS serial no. (unique across both forms together, since a DV links back by it alone; may stay blank). Only Abstract still uses the older single form + table layout.
- **ORS and BURS are twins.** They share the same schema (`tbl_burs_*` mirrors `tbl_ors_*`) and the same server code with the names swapped (`MyOrs`/`MyBurs`, `MyOrsModel`/`MyBursModel`, PDFs). Keep those in sync. The only BURS differences are: FC 07 projects (`fundcluster_id='2'`), blank default particulars, the `burs_date` column, and the BURS form labels. **They have one page:** `myobligation` (sidebar "Obligations › ORS / BURS"; controller `MyObligation`, view `obligation/obligation-main.php`, script `obligation/myobligation.js`). It lists both forms together (each row has `type` `ors`/`burs` and `doc_date`; pills "ORS and BURS / ORS / BURS", `?type=` preselects one) and has one editor whose **Form type** (ORS or BURS) is picked on a new record (only forms the user may add) and fixed once saved; it sets the labels, default particulars, fund cluster, the responsibility codes (FC 01 or FC 07 projects), the Approver Mapping lists (`ors`/`burs` boxes), the History key and the printout. The page only renders the list: loading, saving, certifying and printing go to the form's own endpoint (`myors` / `myburs`: `MAIN-LOAD`, `MAIN-SAVE` with `ors_date`/`burs_date`, `MAIN-APPROVE-A/B`, `PRINT-ORS`/`PRINT-BURS`, `PRINT-DISBURSEMENT`), so each form keeps its own tables, numbering, access codes (26/38 and 27/39) and server checks. Opening `myors` / `myburs` / `my*approval` (MAIN) redirects to `MyObligation::link(type, recid)`, so old links still open the record. The old `ors/ors-main.php`, `burs/burs-main.php`, `myors.js` and `myburs.js` are no longer used. ORS certification goes Box A → Box B, and both steps use the one `ORSAPPROVAL_APPROVE` (38005) code. A certified ORS is locked, and editing a disapproved one resets it to Box A.
- **Disbursement** follows the same pattern. A DV is prepared from an ORS or BURS: `OBLIGATION-LOAD` copies the header and deductions, and sums the lines per responsibility code. Saving writes the DV no. back to that ORS/BURS by `serialno` (only when the DV has one: a blank serial would match every ORS/BURS saved without one). Approval is three steps in order: Box A (supervisor) → Box C (accounting) → Box D (approved for payment), stored in the `certa`, `certc` and `certd` columns (statuses `pending_a`, `pending_c`, `pending_d`, `approved`, `disapproved`). All three use the one `DISBURSEMENTAPPROVAL_APPROVE` (40005) code, but a step can only be decided by the signatory named on that box, matched on `myua_user.full_name` (`certified_a`, `certified_c`, `certified_d`; all three are picked on the DV from Approver Mapping `dv/a`, `dv/c`, `dv/d`. Box D offers ALEXIS M. ORTIZ, ATTY. LUCIEDEN G. RAZ and JACUS S. NACIS, each with an amount range set in Approver Mapping (`min_amount` .. `max_amount`, NULL = no limit): the DV lists every mapped person and selects the one whose range covers its net amount automatically (several: the highest from; `boxDMatch` / `boxDOptions` in the JS), following the amount as it changes until the preparer picks someone else by hand, which is kept (a saved DV keeps its Box D unless it is the one its amount gives). A save rejects a name not mapped to Box D (unless the DV already had it); the range is not enforced on save. It is required; the name is stored as spelled in the mapping. DVs saved before `migration-dv-boxd-pick-11122026.sql` were filled with the Box D their net amount gave under the old tiers). The Administrator role (`fods_is_admin()`) can decide any step. The rule lives in `MyDisbursementModel::can_decide`. A DV is locked once Box A approves it, and editing a disapproved one sends it back to Box A. Every change is logged to `tbl_disbursement_history`, which the editor and the review modal show as a timeline. DV tax rules round each amount to 2 decimals before totaling, which is different from ORS. A DV can have several **other deductions** under any category (Goods, Services, Manual, Payroll, Income Tax; added on top of that category's own deductions) (type + amount each, e.g. a delay penalty per sales invoice) in `tbl_disbursement_deduction` (keyed by `disbursement_id`); the header keeps `other_deductions` as their sum and `deduction_name` as their types joined with "; ", so totals, net, approvals, LDDAP-ADA/RCI and reports read the same fields as before. The save payload adds `dvdeductions_posted=1` plus one `type x|x amount` row each in `dvdeductiondata[]`; a DV saved before this (or copied from an ORS/BURS, which has one) shows its header deduction as one row (`MyDisbursementModel::deduction_rows`). The printout puts each on its own line between NET and Amount Due.
- **LDDAP-ADA and ADA** each have a single approval step (`LDDAPADAAPPROVAL_APPROVE` 41005, `ADAAPPROVAL_APPROVE` 42005). The approval columns are `is_pending`, `is_approved`, `is_disapproved`, `approver` and `remarks` on `tbl_lddapada_hd` and `tbl_ada`. An approved record is locked, and editing a disapproved one sends it back to pending. A DV is paid on one LDDAP-ADA only: a save is refused when a DV it adds (or any of its DVs, when a returned LDDAP-ADA is resubmitted) is on another LDDAP-ADA that is not returned (`is_disapproved = 0`), or is listed twice (`MyLDDAPADAModel::check_dvs_free`); DVs already saved on it are not rechecked, so older doubles stay editable. The DV picker greys such DVs and names the LDDAP-ADA (`on_lddapada` / `on_ids`, returned ones left out). An LDDAP-ADA line's allotment class is the largest-amount UACS on that DV's own ORS/BURS (`MyLDDAPADAModel::dv_lines`). A line's **withholding tax** is the DV's taxes only (VAT/EWT/PT, WTAX, income tax): its total deductions less its other deductions and its non-tax payroll deductions (SSS, HDMF, Pag-IBIG MP2/loan, HMO), `MyLDDAPADAModel::WITHHOLDING_SQL`; the net stays the DV's net, so gross − withholding need not equal net. The printout applies the same rule to lines saved before this (those still holding the DV's full total deductions); any other stored amount prints as saved. ADA prints by `recid` (`dvno` still works for old links). The LDDAP-ADA printout's four signatures (Certified Correct, Approved, Agency Authorized Signatory 1 and 2) are picked on the entry from each signature's own list in **Approver Mapping** (module `lddapada`, box = the field; picking a name fills in its mapped position, which stays editable; a new LDDAP-ADA starts with a box's only mapped person, else blank; a save rejects a name not mapped to that box unless the record already had it). They are stored in `certified_by/_position`, `approved_by/_position`, `ada_approver` (signatory 1, the ADA approver shown on LDDAP-ADA Approval) `/ada_approver_position` and `ada_approver2/_position`. `signatures_for` gives older LDDAP-ADAs (blank columns) the previous fixed names (`MyLDDAPADAModel::SIGNATURES`). These are for printing only; who can approve is still the 41005 access right.
- **RCI** has no approval step. Its cards are Reports, LDDAP-ADAs covered, DVs paid and Total amount, and its year is the encoded date (`created_at`/`created_by`, not `added_*`). Picking an LDDAP-ADA adds one line per DV (`MyRCIModel::lddapada_lines`, which takes the responsibility code from the DV's ORS/BURS). The save payload is 12 `x|x` fields per line.
- **SAOB** (`mysaobrpt`) has no approval step either. The page has two tabs: **Allotments** (cards: Allotments, No revisions yet, With revisions, Approved budget; year = `current_year`) and **Reports** (SAOB PDF/CSV, ORS extraction CSV, monthly report CSV and status PDF, all on their old endpoints). An allotment is one program/project for a year with PS, MOOE and CO lines (`tbl_saob_{ps,mooe,co}_dt`), each carrying 12 `<month>_revision` columns. Revision months (`is_jan` … `is_dec` on `tbl_saob_hd`) are switched on in order; the revision month is the last of an unbroken Jan..N run (`MySaobReportModel::revision_month`, mirrored in JS). A line's proposed realignment is written to that month's column only when the month is switched on by that save; saving again keeps what is recorded. January on locks the approved budget, and the total revised allotment must equal the total approved budget. The save payload is 19 `x|x` fields per line (object code, particulars, UACS, approved, to-date, proposed, revised, then the 12 monthly revisions). The header and its lines are saved in one transaction. "Copy" starts a new allotment from an old one's codes (`?reuse_recid=` still works).
- **PPMP** (`myppmp`, save action `PPMP-SAVE`) has no approval step. Its status comes from two switches on `tbl_ppmp_hd`: `final` (wins when both are on), `indicative`, or `unmarked`. Cards are PPMPs, Indicative, Final and Estimated budget; the year is `fiscal_year`. Items are in `tbl_ppmp_dt` (keyed by `ppmp_id`, and carrying `ppmpno`). The save payload is 15 `x|x` fields per item. The mode of procurement is free text with suggestions (`modes` in `MyPPMP` lookups: the procurement modes from Competitive Bidding to Direct Procurement for Science, Technology and Innovation; older items keep SVP / Public Bidding as saved); `mop` is varchar(100) (`migration-ppmp-mop-11242026.sql`) and wraps in its column on the printout. **Import from Excel** (editor header only, while the user may save; not to be confused with the Documents tab) fills the editor from the office PPMP spreadsheet (.xlsx, .xls, .csv), read in the browser by a local SheetJS copy (`public/assets/libs/xlsx/xlsx.full.min.js`, loaded on first use; `parsePPMP` in `myppmp.js`): header (Fiscal Year, PPMP No., End-User, RC only when it is a known responsibility code, Indicative / Final only when marked), items = rows under the "Column 1 … Column 12" row (size and unit cost found by their titles) until TOTAL BUDGET / Prepared by, signatories = the name under "Prepared by:" / "Submitted by:". MM/YYYY becomes YYYY-MM, GAA / 101 → General Fund. Nothing is saved until Save. **Documents tab** (supporting documents kept with a saved PPMP; a new one shows "Save the PPMP first"): `tbl_ppmp_attachment` (`migration-ppmp-attachments-11242026.sql`), files under `writable/uploads/ppmp/<year>/` through `MyUploadsModel` (any type it allows, 10 MB each, 10 per upload: `MyPPMPModel::DOC_MAX_*`); `DOC-UPLOAD` (`recid` + `attachments[]`) and `DOC-REMOVE` (`id`) take effect at once, no Save (PPMP Add or Update, `MyPPMPModel::can_attach`), return JSON (422 + `error` on failure) and log `DOCUMENT_ADDED` / `DOCUMENT_REMOVED` history; `DOC-FILE&id=` serves a file after a PPMP View check (PDFs and images inline for the preview modal `#ppmpDocModal`, others or `&dl=1` download). `MAIN-LOAD` returns `attachments`. Drop, Add files or paste (Documents tab open) all upload. Quantity × unit cost fills the estimated budget only until someone types a budget. **PRs use up a PPMP** (`MyPPMPUsageModel`, worked out live from the PRs; nothing is stored): a PR line uses a PPMP item when its description and unit match (case and spaces ignored); PRs count oldest first (`added_at`, `recid`), a PR takes from its PPMPs in the order picked and from a PPMP's matching items in their order; a returned PR (disapproved at Box A or B) does not count; what a line asks beyond what is left is "over". The Items tab has a version switcher (`#ppmpVersions`): **Original** (the editable grid), then **Version N · PR …** (read-only, after each PR that used the PPMP: planned, used before, used by this PR, left, amount left; "Fully used" once nothing is left), from `usage` in `MAIN-LOAD` (`versions()`). The list shows "Used N of M" with a bar and has a **Fully used** pill (`summary()`). A used PPMP cannot lower an item below what the PRs took (removing it counts as 0) nor change its PPMP no. (PRs link to it by that string).
- **PR** (`mypr`, main action `PR-MAIN`, save `PR-SAVE`) has two statuses. Its procurement status (`MyPR::statusOf`) is `unnumbered` (no PR no.), `numbered`, or `rfq` (at least one RFQ). Its approval (`MyPR::approvalOf`) works like ORS/PO: Box A (requesting office, `requested_by`, picked on the Certification tab from Approver Mapping `pr/a`; position = the mapped one, else that user record's) → Box B (`approved_by`, not picked: set on save from the estimated cost by `MyPRModel::approver_for`, i.e. the amount tiers of Approver Mapping `pr/b`; a save is refused when no tier covers the amount). The saved `estimated_cost` is the server-side sum of the lines (quantity × unit cost rounded per line), so it always matches Box B. Decisions happen in the PR editor (Approve / Disapprove; approval family 45: `PRAPPROVAL_VIEW` 45001, `PRAPPROVAL_APPROVE` 45005), each box only by the signatory named on it or an Administrator (`MyPRModel::can_decide`). A PR is locked once Box A approves it (`MyPRModel::is_locked`) except for its PR no., which can still be set ("Save PR no."); editing a disapproved PR sends it back to Box A. The PR printout uses the saved signatories (PRs saved before PR approval print the old fixed names). PR approval does not gate the PR no., RFQs or the PO. Anyone who can save PRs (`PR_ADD` for a new PR, `PR_UPDATE` for a saved one) sets the PR no.; there is no procurement-only rule any more. RFQs are open to everyone: `PR_VIEW` to see and print them, `PR_UPDATE` to add one, and the PR must already have a PR no. A PR takes its items from the PPMPs picked (`tbl_pr_ppmp`): `LOAD-PPMP` returns **what is left** of their items (other PRs' use deducted, this PR's own use counted back; `MyPPMPUsageModel::remaining_items`, with `recid`), summed per description and unit. The Details tab's PPMP picker (`#ppmp_options`, `renderPPMPOptions` / `togglePPMP` in `mypr.js`) shows the picked PPMPs as chips (with a count) above a searchable list filtered by fiscal year (defaults to the PR date's year) where a click adds or removes a PPMP (Enter in the search picks the only match); each row shows its status, project, end-user, items and "N of M left" with the amount left and a bar (lookup `ppmps` from `MyPPMPUsageModel::balances()`). Fully used PPMPs are hidden unless "Show fully used" is on, and cannot be picked unless the PR already uses them ("Used by this PR"); picking or removing reloads the items with a toast; a save is refused when a picked PPMP is fully used by other PRs or a line asks for more than its PPMPs have left (`over_for_pr`; lines not on the picked PPMPs are not checked; a locked PR is not checked). Adding or removing a PPMP replaces the items; opening a saved PR shows its saved `tbl_pr_dt` lines, with "Reload from PPMP" to refresh them. RFQs (`tbl_pr_rfq`) are filed under the PR no. string, not the PR's `recid`. The entity name is not on the form: every PR saves and prints `MyPRModel::ENTITY_NAME` (FOOD AND NUTRITION RESEARCH INSTITUTE), the RFQ printout too. The save payload is 5 `x|x` fields per item.
- **PO** (`mypo`, Purchase Order, family 43, tables `tbl_po_hd` / `tbl_po_dt`) is prepared from a numbered PR: `PR-LOAD` copies its PR no., date, charge-to, end-user, fund cluster and items (blank lines skipped) and returns its RFQs, one of which fills the supplier and the delivery / payment terms. The PO keeps `pr_id` only when the PR was picked from the list. PO nos. must be unique. The server computes each line's amount (quantity × unit cost rounded to 2 decimals) and the PO total; the save payload is 5 `x|x` fields per item (stock no., unit, description, quantity, unit cost). **Approval works like ORS**: Box A (accounting, `accountant` picked from Approver Mapping `po/a`, a new PO starts with it when only one person is mapped; position = the mapped one, else that user record's) → Box B (approval, `approved_by`, not picked: set on save from the total by `MyPOModel::approver_for`, i.e. the amount tiers of Approver Mapping `po/b`; a save is refused when no tier covers the total; the JS mirrors it live). Columns `is_pending`, `is_approved_cert{a,b}`, `is_disapproved_cert{a,b}`, `cert{a,b}_remarks`, `cert{a,b}_approver`; statuses `pending_a`, `pending_b`, `approved`, `disapproved`. Decisions happen in the PO editor (Approve / Disapprove; approval family 44: `POAPPROVAL_VIEW` 44001, `POAPPROVAL_APPROVE` 44005), and each box can only be decided by the signatory named on it (matched on `myua_user.full_name`) or an Administrator (`MyPOModel::can_decide`, same rule as the DV). A PO is locked once Box A approves it; editing a disapproved one sends it back to Box A (and recomputes Box B). The printout (`PRINT-PO` on both pages, `procurement/po/po-pdf.php`) is Appendix 61 / FAD-PS-006 on legal paper with the `fnri-header.png` letterhead. The older blank PO template under Abstract (`PO-PRINT`) is unrelated.
- **FODS Assistant** (no access code: everyone signed in has it; no page or sidebar entry) is a floating chat button + panel in the lower right of every page, rendered by `templates/myfooter.php` and driven by `assistant/fods-assistant-panel.js`; the chat UI is the component `assistant/fods-assistant.js` (`FodsAssistant.mount`) + `css/fods-assistant.css`. Questions go to `myassistant?meaction=ASK` (controller `MyAssistant`, model `MyAssistantModel`); opening `myassistant` otherwise redirects to the dashboard. It is an AI chat over FODS data through Groq's OpenAI-compatible API (key and models in `.env`). The AI never writes SQL: it can only call eight read-only "tools" in the model (`get_totals` = the counts behind each page's cards, per `area` (`LIST_AREAS` payees/projects/UACS/supplies/users, plus every `FIND_TYPES` module) and year (default all years, plus `records_per_year`; a year only when the user names one; the year rule mirrors each list page's `yearOf`), with statuses from each module's own `statusOf` / `approvalOf`; `find_record` = any record by its number: ORS/BURS serial, DV, LDDAP-ADA or check, ADA, RCI report, PR, PO, PPMP, budget/SAOB trx no. (`FIND_TYPES`), exact match first, else up to 8 close numbers; returns the record with its lines (8 max) and its trail ORS/BURS → DV → LDDAP-ADA/ADA → RCI, each linked only where the user can open it; its result cap is `MAX_FIND_CHARS`; `get_overview` = the Dashboard's `MyDashboardModel::summary`, `search_obligations`, `search_disbursements`, `my_pending_approvals` (reuses each module's `statusOf` / `can_decide`), `search_payees` (never account numbers or TINs; with no name it returns the payee list totals, the same as the Payees page cards), `search_procurement`), each with fixed parameterized queries that first check the asking user's own module access, so it sees only what that person can open. Answers are capped (rows, result size), use `reasoning_effort: low` on gpt-oss, and switch to `GROQ_FALLBACK_MODEL` when the main model hits its per-minute token limit (429). Per-user limit `RATE_PER_MINUTE` (12). Every question is logged to `tbl_assistant_log` (question, lookups used, status, model; not the answer). The conversation lives in the browser tab (sessionStorage); the last 12 turns go with each question. ## Access control (RBAC)

- Code format: `<2-digit family><3-digit action>`. Actions are 001 View, 002 Add, 003 Update, 004 Delete, 005 Approve. Families run from 20 Payee through 35 RCI, plus 36 Budget Approval, 37 Support Tickets, 38 ORS Approval, 39 BURS Approval, 40 Disbursement Approval, 41 LDDAP-ADA Approval, 42 ADA Approval, 43 Purchase Order, 44 PO Approval, 45 PR Approval and 46 Approver Mapping. **Every approval family has only View and Approve**, kept separate from the entry family's codes: View opens the entry page read-only, Approve decides on it (the separate approval pages are retired, see above). Their hidden `Navigation.php` items (`'hidden' => true`) keep the permissions editor's order. **A new module takes the next family number (47)**, gets constants in `AccessCodes.php`, and gets rows in `tbl_access_modules` named `"<Module> - <Action>"` (the permissions modal splits on `" - "`).
- `tbl_roles` + `tbl_role_access` define roles, and `myua_user.role_id` assigns them. `tbl_user_access` is a per-user **cache** that `MyUserManagementModel::syncUserAccess` regenerates, and the helper reads from it.
- Signatory flags on `myua_user` (`ada_tag`, `cert_tag`, `is_ppmp_signatory`) are separate from module access. Who signs each approval box is set in Approver Mapping, not by these flags; only `is_ppmp_signatory` is still read (the PPMP's own signatory list). None of them is **on the user form**: a new user gets 0 for all three, saving a user never changes them, and they are set directly in the database. Passwords are SHA-512 in `hash_password`, and `is_active` is enforced at login.

## Database conventions

- `tbl_<module>_hd` (header) / `tbl_<module>_dt` (lines). Budget splits use `_direct_{ps,mooe,co}_dt` / `_indirect_{ps,mooe,co}_dt`.
- Every table has `recid` int PK, `added_by`, and `added_at`/`added_on` datetime. Money is `decimal(25,2)`. Flags are `int(11)` 0/1.
- There are no foreign keys. Tables are joined on matching string values (`dvno`, `payee_name`, …).
- Approval columns repeat in each module: `is_pending`, `is_approved_cert{a,b}`, `is_disapproved_cert{a,b}`, `cert{a,b}_remarks`, `cert{a,b}_approver`.

## Adding a module (checklist)

1. Add GET + POST routes with the `myauthuser` filter.
2. Add an entry to `Config/Navigation.php` with its access code(s). Don't hand-edit the sidebar markup.
3. Add the next access-code family in `AccessCodes.php`, plus a migration SQL that inserts the `tbl_access_modules` rows.
4. Write the controller, model, view and JS using an existing modernized module (e.g. `MyPayee`) as the template.
5. Add a migration SQL for the `_hd`/`_dt` tables.

## Gotchas

- The repo has many stale copies (`*_06102025.php`, `* copy.php`, `*.php-backup09292026`, `report-backup/`). Only the unsuffixed file is live. Don't edit the copies.
- Only `/`, `mylogin-auth` and `mylogout` have no auth filter; the SAOB CSV exports (`export-csv`, `monthly-export-csv`, `saob-export-csv`) and `dashboard/saob-session-data` need a login, and the exports also need `SAOB_VIEW`. The `myauthuser` filter also re-reads `myua_user.is_active` on every request, so a deactivated user is signed out on their next click. `MyUserAccount` (old, unrouted) is superseded by `MyAccount`.
- **CSRF and security headers are on** (`Config\Filters` globals). CSRF: `Config\Security` `csrfProtection = 'session'`, `regenerate = false` (one token per session, so polling and several requests in a row work); the token is in `<meta name="csrf-token">` in `myheader.php`, and `public/assets/js/fods-csrf.js` (loaded first in `<head>`) adds it as `X-CSRF-TOKEN` to every same-site POST by patching `XMLHttpRequest` and `fetch` (pages load two jQuery copies, so it is not `$.ajaxSetup`). Native POST forms need `<?= csrf_field() ?>` (login, logout, Abstract). A POST without the token gets 403 (AJAX) or is sent back to the page. Headers: `App\Filters\FodsCsp` sends X-Frame-Options, nosniff, X-Download-Options, X-Permitted-Cross-Domain-Policies, Referrer-Policy and the CSP with `header()` in its **before** step, so FPDF prints / exports that `exit` early get them too (`secureheaders` is off to avoid doubles). The CSP allows only `'self'` + the CDNs in `FodsCsp::CDNS` (+ Google Fonts); a new CDN must be added there or it is blocked. It still needs `'unsafe-inline'` (inline `<script>` data blocks, echoed save scripts, `onclick=`).
- `ExternalApi` and `UacsApi` are small standalone endpoints outside the module pattern.
- An ORS / BURS amount is the sum of its six detail tables (`MyDashboardModel::obligationAmounts`, joined as `LEFT JOIN … a ON a.project_id = h.recid`). The header's `gross_amount` is empty on most older obligations, so don't read it. The detail tables are indexed on `project_id`, `sub_object_code` and `uacs_code`, and the headers on `ors_date` / `burs_date` (`migration-obligation-indexes-11102026.sql`). Still join the aggregate once rather than using a subquery per row.
- **SAOB PDF** (`report/saob-pdf.php`, `SAOB-PDF`) is one long file with a copied block per program group. Its `PDF` class owns page breaks (auto page break is off): `Cell` / `MultiCell` start a new page with the column header when a row would cross `PDF::BOTTOM` (277 mm), later positions of that row are moved to the new page, and an `AddPage()` on a page holding only that header reuses it. Draw rows through `$pdf` as before; don't turn auto page break back on. The signature blocks start a new page only when they don't fit. Category (object code) rows grow with a wrapped label (`$objH`), and a detail row leaves the position one line above its bottom, since the code after it adds one line. In the General Administration section, project titles are trimmed and the relocation project is matched by the start of its title (it is renamed each year, e.g. "… Building (2026)").
